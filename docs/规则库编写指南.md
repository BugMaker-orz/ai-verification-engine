# 规则库编写指南

本指南详细说明如何为 AI 验真引擎编写自定义规则库。规则库采用 YAML 格式，无需编程基础即可编写。

## 1. 规则库结构

一个完整的规则库文件包含以下部分：

```yaml
# 元信息
name: "规则集名称"
version: "1.0"
description: "规则集的简短描述"

# 字段规则（要从文档中提取哪些信息）
fields:
  - name: "字段名"
    required: true或false
    patterns: ["正则表达式1", "正则表达式2"]
    format: null或"date/currency/email/phone/id_card"
    description: "字段说明"

# 条款规则
clauses:
  required:        # 文档中必须包含的条款
    - id: "C-001"
      name: "条款名称"
      keywords: ["关键词1", "关键词2"]
      patterns: ["正则表达式1"]
      severity: "high"
      description: "条款说明"
  forbidden:       # 文档中不能出现的内容
    - id: "F-001"
      name: "禁止内容名称"
      keywords: ["关键词1"]
      patterns: ["正则表达式1"]
      severity: "critical"
      description: "说明"

# 跨文档一致性规则（多份文档之间哪些字段必须一致）
cross_document:
  - id: "X-001"
    name: "规则名称"
    fields: ["字段名1", "字段名2"]
    severity: "high"
    description: "说明"
```

## 2. 元信息

| 字段 | 必填 | 说明 | 示例 |
|------|------|------|------|
| `name` | 是 | 规则集名称，会显示在报告中 | `"通用合同与文档验真规则"` |
| `version` | 是 | 版本号，建议语义化版本 | `"1.0"` |
| `description` | 否 | 规则集简短描述 | `"适用于商业合同、协议类文档的验真"` |

## 3. 字段规则 (fields)

字段规则定义了引擎要从文档中提取哪些结构化信息。

### 3.1 字段定义

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | 字段名称，必须唯一，跨文档规则通过此字段名引用 |
| `required` | 是 | 是否必填。`true`=缺失时报 high 级问题；`false`=缺失不报错 |
| `patterns` | 是 | 正则表达式列表，按顺序尝试，任一匹配即提取。匹配到的第一个捕获组作为字段值 |
| `format` | 否 | 格式校验类型。可选值：`date` / `currency` / `email` / `phone` / `id_card` / `null` |
| `description` | 否 | 字段说明，用于补位建议和 AI 提示词 |

### 3.2 正则表达式编写要点

**基本格式**：`"关键词[:：]\\s*(.+)"`

- `[:：]`：匹配中文冒号或英文冒号（两种都要覆盖）
- `\\s*`：匹配冒号后可能的空格
- `(.+)`：捕获冒号后面的所有内容作为字段值
- 注意：YAML 中反斜杠要写两个（`\\`）

**常见字段正则示例**：

```yaml
fields:
  # 甲方名称
  - name: "甲方/委托方"
    required: true
    patterns:
      - "甲方[:：]\\s*(.+)"
      - "委托方[:：]\\s*(.+)"
      - "买方[:：]\\s*(.+)"
    format: null
    description: "合同甲方/委托方/买方的名称"

  # 合同金额（支持多种表述）
  - name: "合同金额"
    required: true
    patterns:
      - "合同金额[:：]\\s*(.+?)(?:元|人民币|$)"
      - "总金额[:：]\\s*(.+?)(?:元|人民币|$)"
      - "合同总价[:：]\\s*(.+?)(?:元|人民币|$)"
    format: currency
    description: "合同总金额"

  # 签订日期
  - name: "签订日期"
    required: true
    patterns:
      - "签订日期[:：]\\s*(.+)"
      - "签署日期[:：]\\s*(.+)"
      - "签订于[:：]\\s*(.+)"
    format: date
    description: "合同签订日期"
```

### 3.3 格式校验 (format)

| 格式值 | 校验内容 | 示例有效值 |
|--------|---------|-----------|
| `date` | 日期格式 | `2024-01-15`、`2024年1月15日`、`2024/01/15` |
| `currency` | 金额格式 | `280000元`、`28万元`、`¥280,000` |
| `email` | 邮箱格式 | `example@company.com` |
| `phone` | 手机号格式 | `13800138000` |
| `id_card` | 身份证号格式 | `110101199001011234` |
| `null` | 不校验 | 任意文本 |

## 4. 条款规则 (clauses)

条款规则分为两类：`required`（必须包含）和 `forbidden`（禁止出现）。

### 4.1 必含条款 (required)

文档中必须包含的条款，缺失时报对应严重度的问题。

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | 是 | 规则唯一标识，建议格式 `C-REQUIRED-XXX` |
| `name` | 是 | 条款名称，显示在报告中 |
| `keywords` | 否 | 关键词列表，文档中出现任一关键词即认为条款存在 |
| `patterns` | 否 | 正则表达式列表，任一匹配即认为条款存在 |
| `severity` | 是 | 严重度：`critical` / `high` / `medium` / `low` |
| `description` | 否 | 条款说明，用于补位建议和 AI 提示词 |

> `keywords` 和 `patterns` 至少填一个。AI 模式下，即使关键词未命中，AI 也会做语义二次判断。

**示例**：

```yaml
clauses:
  required:
    - id: "C-REQUIRED-001"
      name: "违约责任条款"
      keywords: ["违约责任", "违约金", "违约赔偿"]
      patterns: ["违约.{0,10}(责任|赔偿|金)"]
      severity: "high"
      description: "合同应约定一方违约时应承担的责任"

    - id: "C-REQUIRED-002"
      name: "争议解决条款"
      keywords: ["争议解决", "管辖", "仲裁", "诉讼"]
      severity: "high"
      description: "合同应约定争议发生时的解决方式和管辖机构"
```

### 4.2 禁止条款 (forbidden)

文档中不能出现的内容，出现时报对应严重度的问题。

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | 是 | 规则唯一标识，建议格式 `C-FORBIDDEN-XXX` |
| `name` | 是 | 禁止内容名称 |
| `keywords` | 否 | 关键词列表，出现任一即触发 |
| `patterns` | 否 | 正则表达式列表，任一匹配即触发 |
| `severity` | 是 | 严重度 |
| `description` | 否 | 说明为什么禁止、建议怎么改 |

**示例**：

```yaml
clauses:
  forbidden:
    - id: "C-FORBIDDEN-001"
      name: "空白占位符未填写"
      keywords: []
      patterns: ["_{3,}", "TODO", "待填写", "XXX"]
      severity: "critical"
      description: "文档中存在未填写的空白占位符，必须补充完整"

    - id: "C-FORBIDDEN-002"
      name: "最终解释权条款"
      keywords: ["最终解释权", "解释权归"]
      patterns: ["最终解释权.{0,10}(归|属于)"]
      severity: "high"
      description: "此类条款可能被认定为无效格式条款，建议删除"
```

## 5. 跨文档规则 (cross_document)

跨文档规则定义了多份文档之间哪些字段必须保持一致。

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | 是 | 规则唯一标识，建议格式 `X-DOC-XXX` |
| `name` | 是 | 规则名称 |
| `fields` | 是 | 字段名列表（必须与 `fields` 中定义的 `name` 完全一致） |
| `severity` | 是 | 严重度 |
| `description` | 否 | 说明 |

**示例**：

```yaml
cross_document:
  - id: "X-DOC-001"
    name: "甲方名称一致性"
    fields: ["甲方/委托方"]
    severity: "high"
    description: "所有文档中的甲方名称应完全一致"

  - id: "X-DOC-002"
    name: "合同金额一致性"
    fields: ["合同金额"]
    severity: "critical"
    description: "主合同与补充协议中的合同金额应一致"
```

**冲突检测逻辑**：
- 数值型字段（含"金额/数量/期限"等关键词）：提取数值比对，允许单位差异（如"28万元"="280000元"）
- 日期型字段：归一化为 `Y-M-D` 后比对
- 文本型字段：归一化（去空白、全角转半角、小写）后比对
- AI 模式下：基础检测到不一致后，AI 做语义二次确认，排除误报

## 6. 严重度说明

| 严重度 | 扣分 | 颜色 | 适用场景 |
|--------|------|------|---------|
| `critical` | 25 | 红色 | 致命问题：空白未填、金额不一致、主体名称错误 |
| `high` | 10 | 橙色 | 重要问题：必填字段缺失、必含条款缺失、甲方/乙方不一致 |
| `medium` | 4 | 黄色 | 一般问题：格式不合法、模糊表述、次要条款缺失 |
| `low` | 1 | 蓝色 | 轻微问题：建议优化的表述、非关键信息缺失 |
| `info` | 0 | 灰色 | 提示信息，不扣分 |

## 7. 完整示例

以下是一个简化的招投标文件验真规则库：

```yaml
name: "招投标文件验真规则"
version: "1.0"
description: "适用于招标文件、投标文件、中标通知书的一致性验真"

fields:
  - name: "项目名称"
    required: true
    patterns: ["项目名称[:：]\\s*(.+)", "工程名称[:：]\\s*(.+)"]
    format: null
    description: "招标项目名称"

  - name: "招标编号"
    required: true
    patterns: ["招标编号[:：]\\s*([A-Z0-9-]+)", "项目编号[:：]\\s*([A-Z0-9-]+)"]
    format: null
    description: "招标项目唯一编号"

  - name: "投标截止时间"
    required: true
    patterns: ["投标截止时间[:：]\\s*(.+)", "投标截止[:：]\\s*(.+)"]
    format: date
    description: "投标文件递交截止时间"

  - name: "中标金额"
    required: false
    patterns: ["中标金额[:：]\\s*(.+?)(?:元|人民币|$)", "中标价[:：]\\s*(.+?)(?:元|人民币|$)"]
    format: currency
    description: "中标单位的投标报价"

clauses:
  required:
    - id: "C-REQUIRED-001"
      name: "评标办法"
      keywords: ["评标办法", "评标方法", "评审标准"]
      severity: "high"
      description: "招标文件应明确评标办法和评审标准"

    - id: "C-REQUIRED-002"
      name: "投标保证金"
      keywords: ["投标保证金", "保证金"]
      severity: "medium"
      description: "招标文件应说明投标保证金金额和缴纳方式"

  forbidden:
    - id: "C-FORBIDDEN-001"
      name: "倾向性条款"
      keywords: ["指定品牌", "指定供应商", "唯一供应商"]
      severity: "high"
      description: "招标文件不得含有倾向性、排他性条款"

cross_document:
  - id: "X-DOC-001"
    name: "项目名称一致性"
    fields: ["项目名称"]
    severity: "high"
    description: "招标文件、投标文件、中标通知书中的项目名称应一致"

  - id: "X-DOC-002"
    name: "招标编号一致性"
    fields: ["招标编号"]
    severity: "high"
    description: "所有文件中的招标编号应一致"
```

## 8. 编写建议

1. **从通用规则复制修改**：复制 `rules/general_contract.yaml`，在此基础上增删字段和条款
2. **关键词要全面**：同一个概念可能有多种表述（如"甲方"="委托方"="买方"），尽量都覆盖
3. **正则从简到繁**：先写简单的关键词匹配，发现漏检再逐步加正则
4. **严重度要合理**：critical 只给最致命的问题，不要滥用
5. **测试验证**：写完后用已知问题的文档测试，确认能检测到预期问题
6. **AI 模式兜底**：即使关键词没覆盖全，AI 模式下也能做语义匹配，不必追求 100% 关键词覆盖

## 9. 规则库存放与使用

- 规则库文件放在 `rules/` 目录下，文件名以 `.yaml` 结尾
- Web 界面会自动列出 `rules/` 目录下所有规则库供选择
- 命令行使用 `-r rules/你的规则库.yaml` 指定
- Python API 使用 `VerificationEngine(ruleset_path="rules/你的规则库.yaml")`
